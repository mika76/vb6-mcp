# T14: debug a reported bug (2026-10-17, Sonnet, dry run)

## The task

`tests\fixtures\Cart` (written by `bench\make-cart-fixture.cs`) is an order form: price, quantity, Add, Clear, a list of the lines and a total. The third and later lines get 10% off (`modPricing`). The program has a **planted bug**, marked only in the generator, never in the VB6 files:
- `frmCart` keeps one module-level `Private m_line As New clsLine` and adds that same object for every line.
- So every line in the collection becomes the last one entered.
- The list box still looks right, because its text is taken at the moment a line is added. Only the total is wrong, and only once two different lines are in the order.

The prompt gives only the user's report: 10×1, 20×2, 5×4 shows "Total: 58.00", but it should be 68.00. The agent must find the cause, make the smallest right fix, check it by running the program, and save.

**Scoring** (`Verify-Task T14`):
- The fix is saved, and the discount rule (`position > 2`) is kept.
- The project builds.
- `bench\replay-cart.ps1` drives the built EXE with plain Win32 messages, independent of the tools under test. It enters 10×1, 20×2, 5×4 (expects 68.00), then Clear, then 3×2, 7×1 (expects 13.00). The second scenario catches fixes tuned to the reported numbers only.
- Recorded alongside: the lines changed per file, and `ranProgram` (`run_start`/`exe_run`, or a shell command that starts `Cart.exe`).

Checked both ways before any run. The fixture's own build replays 58.00 and 14.00. A copy with the one-line fix (`Set m_line = New clsLine` in `cmdAdd_Click`) replays 68.00 and 13.00.

## Dry run (1 run each)

| | Result | Tokens | Cost | Time | Tool calls | UAC | Lines changed | Ran it |
|---|---|---|---|---|---|---|---|---|
| A (no tools) | correct, not unaided | 385,793 | $0.17 | 152 s | 15 | **1** | 1 | yes |
| B (vb6 tools) | correct, unaided | 350,958 | $0.14 | **30 s** | 19 | 0 | 1 | yes |

- **B:**
  - Read the handler (`proc_get`), ran the program in the IDE (`run_start`) and reproduced 58.00 with `app_set_text` and `app_click`.
  - Fixed it with `proc_replace`, ran it again and saw 68.00, then `run_end` and `project_save`.
  - It named the cause correctly, and it pointed out that VB added an `IconForm` line to the `.vbp` when it saved.
- **A:**
  - Read the files and edited the form with Edit.
  - Built a test copy with `VB6.EXE /make` into its scratch folder, which cost one UAC prompt that someone approved.
  - Drove the form through PowerShell Win32 calls to see 68.00, and didn't re-check the 58.00 case.
- Both made the same one-line fix and kept the discount rule. Neither used the debugger: the cause can be read off the code once the symptom is known.

## What it shows

- Both configs can solve a bug this size. B is 5× faster and needs no prompt, because it reproduces and checks the fix inside the IDE. A has to compile first, elevated, and then write its own UI automation.
- The task doesn't yet need the debugger. A variant where the cause isn't visible in the code would test `bp_toggle`, `debug_locals` and `debug_eval`: for example, data from a file, or state built up over many clicks.
