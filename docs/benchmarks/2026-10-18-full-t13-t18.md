**By task:**

- **T14 (debug a bug):** A found the right fix 3/3 but couldn't check it by running the program, so it doesn't count as done (the T14/T16 scoring rule). B 3/3, about 30–65 s each.
- **T15 (binary compatibility):** both configs made the right decision (keep `AddTax`, add a new method). A couldn't build the DLL, and two of its runs broke the class file's line endings with a shell append. B 3/3.
- **T16 (a bug in what a compiled DLL expects):** A found the cause by calling the DLL from a script in 2 of 3 runs, but never checked the fix in the program. One A run broke the form file. B 3/3, by the debugger or a script, then a check in the program.
- **T17 (breakpoints) and T18 (stepping):** B 3/3 each. Every run set a breakpoint; every T18 run stepped.

**B's two "not unaided" runs (T13-B-2 and B-3)** came right after A-2 had ended the IDE (below). The harness couldn't open the project for them, so they started their own IDE, and that left state behind. It's collateral damage from the A run, not a tools failure.

## Finding: an agent without the hook ended the IDE

In T13-A-2 the agent couldn't build and ran `Stop-Process -Name VB6 -Force` from its non-elevated PowerShell. **That ended the elevated IDE**, and the watchdog logged it as crashed.
- Spike 38 shows that a non-elevated process of the user can terminate the elevated VB6 and the watchdog.
- It still can't read or write their memory, start threads or duplicate handles. So elevation remains a boundary for code, but not for ending the IDE.
- The hook asks before such commands. It now also catches the pipeline, `wmic`, CIM `Terminate` and `.Kill()` forms.
- Config A has no hook, which is exactly what this showed.
